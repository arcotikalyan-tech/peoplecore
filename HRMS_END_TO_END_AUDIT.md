# PeopleCore HRMS — End-to-end audit

Audit date: 2026-10-27. Code audited: branch `next/posh-cases` at commit `7aaf930` in `~/Projects/peoplecore-dev` (identical to `main` plus one unpushed phone fix). This file is the only file the audit created; no application source, schema, dependency or production data was changed by the audit.

**How to read the statuses.** WORKING = implementation traced and covered by a passing automated test (named). PARTIAL = exists but an important piece is missing. BROKEN = an identified defect stops it working as intended. MISSING = not built. UNVERIFIED = could not be confirmed without a running production system, a device scenario or legal advice. NOT APPLICABLE = outside product scope.

**How findings were established.** Six read-only reviews traced UI → server action / API → RLS policy or RPC → database tests. The three most serious claims (employee `user_id` re-linking, client-supplied payroll results, `safeNextPath`) were re-checked line by line for this report. Where a defect was found by reading code but not executed, it is marked *code-confirmed*. Two defects were reproduced on a real Pixel against the live site (marked *seen on device*).

---

## 1. Executive summary

**Overall.** PeopleCore is a broad, India-focused, multi-tenant HRMS with real depth: 224 database tables all under row-level security, a shared approvals engine, a leave ledger, a payroll engine with maker-checker, recruitment through to offboarding, and 722 passing automated tests plus 65 browser test files. The core of the product is built and mostly tested. It is **not yet ready to run payroll for real customers at scale** because of a small number of P1 defects in payroll integrity, attendance trust, large-organisation data limits and the Android release process. No P0 (immediate data breach) issue was found.

| Area | Readiness | Why |
|---|---|---|
| Web application | Good, with P1 gaps | 90 pages, all guarded; dashboards and People list wrong above ~1,000 rows |
| Android application | Not release-ready | Selfie check-ins never reached the server (fixed today, not yet released); debug-key signing; shared-phone and offline-queue defects |
| Backend / database | Strong, with P1 gaps | RLS everywhere, tested tenancy; payroll results and punch inputs trusted from the client |
| Security | Good | No P0; seven P2 auth-edge issues (redirect, reset path, session revocation) |
| Testing | Good for DB and web, weak for mobile and payroll figures | 722 unit/DB tests pass; no Android build or device test in CI; statutory report figures untested |
| Operations | Weak | No error monitoring, no worker health check, storage not backed up, deploy can run ahead of schema |

**Critical blockers (P1, must fix before real payroll / wider rollout):**
1. HR executives can re-link any employee record to their own sign-in (code-confirmed). → EMP-01
2. Stored payroll results come from the browser and are not re-verified; the checker approves inputs, not stored figures (code-confirmed). → PAY-01
3. Two open payroll runs can pay the same reimbursement, arrear or loan EMI twice (code-confirmed). → PAY-02
4. Attendance can be gamed by calling the punch function directly (time up to 1 h back unflagged, accuracy, method, IP) (code-confirmed). → ATT-01, ATT-02
5. Unpaid leave spanning a weekend deducts the weekend from pay (code-confirmed). → ATT-03
6. Attendance and leave can change after payroll is locked with no adjustment (code-confirmed). → ATT-04
7. Lists and dashboard figures silently stop at 1,000 rows (code-confirmed; live limit UNVERIFIED). → DATA-01
8. Android: selfie check-ins never uploaded (seen on device; fixed in `7aaf930`, not released); shared-phone queue credits the wrong person; queue race loses punches; release APK signed with the public debug key. → MOB-01..05

**Major missing modules (optional unless the business needs them):** travel requests, surveys/polls, LWF and statutory bonus calculation, professional tax outside Karnataka and Maharashtra, tax-proof uploads, document expiry tracking, e-signature.

**Audit limitations.** Production configuration (Supabase Auth session settings, PostgREST `max_rows`, backups/PITR) could not be read — reading production was refused by the permission policy. Browser tests were not run locally (machine out of memory); the CI run is used instead. No statutory rule is certified; all are flagged for verification against official sources. Only one device scenario (check-in) was tested by hand.

## 8. Database and API findings

- **Trust boundary:** two important RPCs trust client data (PAY-01 `store_payroll_results`, ATT-01/02 `record_punch`).
- **Row cap:** application code assumes more than PostgREST's 1,000 rows (DATA-01).
- **Missing locks:** leave balance check (LV-01); phone queue (MOB-04); no concurrent-approval test (APR-01).
- **Period integrity:** no payroll-lock guard on attendance/leave changes (ATT-04); double inclusion across open runs (PAY-02).
- **Column-level control:** `employees` and `employment_records` are updatable column-wide by `employee.update` (EMP-01, EMP-02).
- **Hardcoded statutory constants** outside the rule set (12%, ₹15,000, 0.75%, 3.25%) in `payroll_statutory_rows`, ECR route and report headers (PAY-04).
- **Stale docs:** `docs/04` (encryption), `docs/07` T19, `docs/09` (anon functions), runbooks (Vercel).
- **Strengths:** RLS on every table with tests; explicit grants; composite org FKs; append-only audit tables; idempotent punches and jobs; effective-dated history with no-overlap constraints.

1. **What already works?** Tenancy and RLS, roles and permissions, two-step sign-in, core HR records and history, import, org structure, recruitment, onboarding, offboarding and F&F, assets, documents, the approvals engine, the leave ledger, daily attendance rules, payroll maker-checker and payslip privacy, expenses, helpdesk, announcements, grievances, learning catalogue, reports access and export logging, the worker's scheduled jobs and push.

3. **Missing?** Travel, surveys, LWF, statutory bonus, PT beyond KA/MH, tax proofs, document expiry, sandwich rule (advertised), legal-entity UI, error monitoring, Android CI and proper release signing, staging.
4. **Broken?** Payroll result trust and double payment, punch trust, LOP over weekends, changes after lock, night-shift regularization, 1,000-row truncation, compliance tile, phone queue on shared devices and under races, selfie check-in upload in the released app (fixed, unreleased).
5. **Security / employee-data risks?** EMP-01, PAY-01, ATT-02/SEC-04, MOB-03, MOB-05, SEC-01..03.
6. **Dashboards needing changes?** Admin/HR (compliance, presence, attrition, holidays), payroll (missing tiles), manager (team tiles), platform (metrics).
7. **Missing on Android vs web?** Attendance history, half-day leave, expenses, documents, announcements, directory, helpdesk; some are deliberate web-only.
8. **Must fix before production release?** Groups 1 and 2 of §11 (T1–T14).
9. **Develop next?** After T1–T14: dashboards (Group 3), payroll verification (Group 5), monitoring and backups (Group 6).
10. **Cannot yet verify, and evidence needed?** Production Supabase settings and `max_rows` (dashboard access), backup/PITR plan (Supabase plan page), statutory values (adviser sign-off), shared-device and offline behaviour (device test), redirect behaviour in browsers (manual test), the in-progress CI run for `a94d34f`.
